# デザイン改善ワークフロー（後段改善前提）

## 方針

- 現フェーズは機能実装を優先し、UIは後で改善する前提で進める。
- 画面ロジック（Usecase/Repository）と見た目（UIコンポーネント）を分離し、後から差し替え可能にする。
- 主要導線の正しさを先に担保し、デザイン品質は改善フェーズで引き上げる。

## 改善タイミング

- MVP主要導線（DistanceMode -> DrawingScreen -> WaitingScreen -> ResultScreen）が安定した後に実施する。
- 仕様変更が多い期間は大規模な見た目変更を避ける。

## 改善手段

### 1. v0 を使う場合

- 画面の叩き台（レイアウト、コンポーネント構成）を短時間で作る用途に限定する。
- 生成したUIはそのまま採用せず、既存要件と遷移仕様に合わせて調整する。
- データ取得や業務ロジックは既存のUsecase経由に統一する。

### 2. Codex skills を使う場合

- UI改善タスク（コンポーネント分割、スタイル整理、命名統一）を反復的に進める用途で使う。
- スキル適用時も `doc/requirements.md` の画面I/O契約と統合ルールを優先する。

## 受け入れ基準（デザイン改善フェーズ）

- 操作導線が壊れていない（既存遷移が維持される）。
- 主要画面で情報の優先順位が明確（主操作が1目で分かる）。
- レスポンシブ（iPad/iPhone）で崩れない。
- `npm run build` が成功する。

## 非対象（現時点）

- 本番デプロイ向けの最終ビジュアル調整
- アニメーション最適化
- デザインシステムの完全整備
